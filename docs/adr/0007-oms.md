# ADR 0007 — Order Management System

Status: accepted (phase 5). Code: `src/trader/oms/`, `src/trader/risk/gate.py`, `src/trader/domain/exits.py`.
Spec: SPEC §6, §15 (startup and shutdown). Acceptance tests: `tests/integration/test_oms_properties.py`,
`tests/integration/test_restart_mid_order.py`.

## Single writer per account

`OrderManager` owns all order and position state for one account. Every mutation is a job on one `asyncio`
queue, run by one writer task:
- broker events (`on_broker_event`, `on_tick`);
- commands (`submit`, `modify_order`, `cancel_order`, `modify_position`, `close_position`, `close_all`,
  `flatten`, `reconcile`);
- timers.

Broker calls that can be slow, such as sends, cancels and closes, run as separate tasks. They post their
outcome back to the queue as another job, so the writer never waits on the network while events queue up.
The exceptions are reconcile and `find_order` lookups: these run inside the writer, because their result
must be applied atomically against the state they diffed.

After any job that changed state, the writer persists an `OmsState` snapshot. `flush()` is a barrier: it
waits until everything queued so far has been applied.

`AccountRuntime` wires one broker adapter to the OMS (and to market data). Its pump is the only consumer of
`broker.events()`. Start order: OMS restore → connect → instruments → pump → subscribe → wait for the first
successful reconcile (`ready`) → warm-up. Strategies must not start before `ready`.

## Submit path

`Strategy → OrderIntent → RiskGate.pre_trade(intent, view) → OrderManager → Broker`.

1. **Risk.** The OMS calls `RiskGate.pre_trade(intent, AccountView)` and publishes a `RiskEvent` for every
   decision. The composition root always builds a `RiskEngine` (phase 6); `ApproveAll` is for tests only.
   No other way into the OMS exists. Manual API and Telegram orders use the same `submit`, and changes to
   orders and stops go through `RiskGate.pre_modify` / `pre_modify_position` (phase 12, ADR 0008).
2. **Capabilities.** Missing broker features are emulated; the OMS never checks the broker's name:

   | Missing capability | What the OMS does |
   |---|---|
   | GTD/DAY expiry | sends GTC and cancels locally at the deadline |
   | Native SL/TP | sends the entry without them and watches them locally from the fill (the emulated stop/target closes the position) |
   | STOP_LIMIT | the order waits locally (WORKING, nothing at the broker). When the stop trades, it sends a LIMIT, or a MARKET capped by `max_slippage` when the limit is already marketable |
   | Trailing, break-even, time exit, scale-out (`domain/exits.py`) | always run in the OMS on live ticks |
   | OCO | an OCO group cancels its siblings when one member fills |

   `native_sl_tp` covers SL/TP both on the entry and on the position; every current adapter has it, so
   brackets go out natively. SPEC §6's "attach right after the fill" needs a broker that can hold position
   SL/TP but not take them on the entry. That broker would get its own capability flag and an attach step;
   none of ours needs it.
3. **PENDING_SUBMIT is persisted (awaited) before the request leaves.** A crash after this point leaves a
   record that the next process resolves. The broker request carries the ULID `client_order_id`, and every
   retry reuses it.

## Outcomes and retries

| Outcome | Action |
|---|---|
| ACK | ACCEPTED; later broker events move the order forward |
| Retryable error (`BrokerError.retryable`: `Requote`, `RateLimited`, `BrokerUnavailable`, `AuthExpired`) | resend with the same id after `retry_backoff × attempt` (or `retry_after_ms`), while `attempts < max_attempts` and the signal is fresh |
| `UnknownOrderState` (lost connection, timeout after sending) or no ACK within `ack_timeout` | UNKNOWN, then after `unknown_grace` a targeted lookup: `broker.find_order(cid, since)` |
| Other errors | REJECTED with the reason |

**Targeted lookup (`_resolve`).**
- Found: the broker's view wins. The OMS syncs status, prices and fills (`order_resolved`).
- Not found, still PENDING_SUBMIT or UNKNOWN: if the signal is fresh (`now − signal_ts ≤ resubmit_window`)
  and attempts remain, the OMS resends with the same id (`order_resubmitted`). Otherwise it gives up
  (`order_abandoned` → REJECTED).
- Not found, but previously open: CANCELLED (`order_missing`).

When the adapter's `Capabilities.idempotent_submit` is false, a resend is not de-duplicated by the server.
The OMS then needs two "not found" lookups, `unknown_grace` apart, before it resends, so a first send that
is still in flight is not doubled.

The window exists because a market signal from minutes ago is not the trade the strategy wants now.

### What makes `find_order` exact per broker

| Broker | Lookup | Resend safety |
|---|---|---|
| paper | by client id | idempotent |
| cTrader | open orders (`ProtoOAReconcileReq`) plus order history (`ProtoOAOrderListReq`) carrying `clientOrderId`. A truncated (`hasMore`) window is bisected; if it is still too dense the lookup raises instead of returning a false "not found" | not idempotent: two lookups before a resend |
| Exness | entities carry no client id, so only orders this adapter instance linked can be found | idempotent by key: the server returns the original `operation_id` and does not execute again |

**Exness after a restart.** The new adapter cannot find the order, so the OMS resends it with the same
key. The server de-duplicates it, so no `transaction_event` follows. The adapter's operation watchdog then
re-links the order by content within the operation's lifetime:
- a market open via its `open` deal (closing orders look identical in order history);
- a pending order via the snapshot (still working) or order history (finished).

It requires exactly one untagged match; an ambiguous match is left unlinked (logged). It then
resubscribes, and the reconcile that follows resolves the order and re-attributes the position. The demo
probe `test_probe_restart_relink_from_history` settles the history fields this relies on.

## Applying broker state

- **Never backwards.** Status changes are rank-based (PENDING_SUBMIT < ACCEPTED < WORKING <
  PARTIALLY_FILLED < terminal). A stale view is ignored, and terminal states absorb. Every applied change
  goes through `state_machine.transition`/`apply_fill`, so the history is always a legal path.
- **Fills** are de-duplicated by `fill_id` (bounded set, persisted). An order view with more filled volume
  than we know applies a *synthetic* fill for the difference. The real deals consume it when they arrive,
  so volume is never counted twice.
- **Attribution.** `position_id → strategy_id` is learned from our fills (and from adapters that tag
  positions) and persisted. A broker position we cannot attribute is adopted as `manual` and still counts
  toward risk.

## Reconciliation

Runs at startup, on every connection UP, and every `reconcile_interval`. It snapshots the broker and diffs
it against local state; the broker wins. Every correction is a `ReconcileEvent` with before/after:

| Kind | Meaning |
|---|---|
| `position_adopted` | a broker position we cannot attribute, adopted as `manual` |
| `position_restored` | a broker position we can attribute, restored to its strategy |
| `position_corrected` | a known position whose volume, SL/TP or attribution differs from the broker |
| `position_missing` | a position we track that the broker no longer has |
| `order_adopted` | a broker order we did not know about |
| `order_corrected` | a known order whose status or prices differ from the broker |

Local open orders that the broker does not list go through the targeted lookup above. `ready` is set only
after a successful reconcile, and `submit` refuses new orders until then. Closes and cancels are not
blocked; they only reduce risk.

## Emulation engine (`oms/emulation.py`)

The engine is pure: no IO, no clock. Ticks and timer calls go in and actions come out (`ModifyStop`,
`ClosePosition`, `CancelOrder`, `SendStopLimit`); the OMS executes the actions.

- Exit price is the bid for longs and the ask for shorts.
- Trailing moves only in the position's favour, by at least `max(step, tick)`, and at most once per
  `min_modify_interval`.
- Scale-out rounds down to `volume_step`. The last level, or a remainder below `min_volume`, closes the rest.

The engine's state is part of `OmsState`, so emulations survive restarts.

## Store

`OmsStore` is a port with `load()` and `save(OmsState)`. The JSON schema is `oms/1`. `JsonFileStore`
writes atomically (temp file + fsync + rename) with 0600 permissions. `MemoryStore` round-trips through
JSON so tests catch serialisation bugs.

The Postgres event store and async writer come in phase 9 behind the same port. Until then one JSON file
per account is the durable record. Writes are full snapshots, which is fine at this account size. Finished
orders and fill ids are bounded (`keep_finished`, `keep_fill_ids`).

## Testing

- `test_oms_properties.py` (hypothesis): random sequences of order views and fills — stale, duplicated,
  addressed by client id or only by broker id. Checked invariants:
  - no status regression, and terminal states absorb;
  - `filled ≤ volume` and never decreases;
  - FILLED ⇔ fully filled;
  - a re-delivered deal changes nothing;
  - every history step is a legal transition;
  - the writer never fails.
- `test_restart_mid_order.py`: the process is killed (`AccountRuntime.abort`) after PENDING_SUBMIT was
  persisted, and a new process starts with the same store:
  - paper, crash after the broker received the order: found, not resent;
  - paper, crash before the send: resent once with the same id;
  - paper, long outage: abandoned instead of sending a stale signal;
  - cTrader fake: found in order history;
  - Exness fake: idempotent resend, history re-link, resolved, position re-attributed.

  Each scenario ends with exactly one position, attributed to the strategy (none for the abandoned case).
- `test_oms.py`: lifecycle, retries, UNKNOWN handling, reconcile after reconnect, close-all/flatten, OCO,
  trailing, and emulated stop-limit/SL/TP/expiry on a broker with those capabilities removed.

## Consequences

- One slow lookup (cTrader history bisect, at most 64 historical requests) blocks that account's writer.
  Accepted: it is rare and the result must be applied atomically. Other accounts are unaffected.
- `ApproveAll` must not reach a demo or live config. Phase 6 wires the real `RiskEngine` in the composition
  root.
