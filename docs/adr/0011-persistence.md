# ADR 0011 — Persistence: event store, async writer, outage buffer

Status: accepted (phase 9). Code: `src/trader/persistence/` (`schema.py`, `migrations/`, `serialize.py`,
`sink.py`, `writer.py`, `wal.py`, `service.py`), wired in `trader.app.App`. Spec: SPEC §12.

Acceptance: **DB kill test: trading continues, data replayed** (`tests/integration/test_db_kill.py`, on a
real PostgreSQL).

## What goes where

| Data | Where |
|---|---|
| Ticks, broker candles | Parquet (phase 4), never PostgreSQL |
| OMS snapshot, risk state, strategy state, fill ledger, journal, executions, equity curve | Local files (phases 5–8), always written: they are what a restart restores from, with or without a database |
| Everything else, durably and queryably | **PostgreSQL** |

The PostgreSQL side has two parts:
- **`events`**, the append-only event store: every domain event except ticks and bars, plus journal
  trades, strategy state, reference data and audit entries, as JSONB. It is the audit trail and the future
  replay source.
- **Projections** for queries, fed by the same records: `orders` (latest state), `order_events` (every
  status change, by history index), `fills`, `positions` + `position_history`, `account_snapshots`,
  `risk_events`, `reconcile_events`, `trades`, `strategies`, `strategy_state`, `accounts`, `instruments`,
  `audit_log`.

Money and prices are `NUMERIC` (exact). Times are `TIMESTAMPTZ` in UTC.

**Schema:** Alembic manages it (`migrations/versions/0001_initial_schema.py`, autogenerated from
`schema.py`; `alembic check` reports no drift). `trader run` upgrades to head on its first successful
connection. It can also be run by hand: `TRADER_DB_URL=… uv run alembic upgrade head`.

**URL:** it comes from `TRADER_DB_URL` (`database.url_env`), never from a file. Configuring `database:`
without the variable is a startup error.

## Writer (`DbWriter`)

1. **Submitting:** `submit(record)` is synchronous and only queues, so trading never waits on the database.
   Every record gets a ULID `record_id`.
2. **Batching:** a background task writes batches of up to 500 records, flushed every 200 ms, **one
   transaction per batch**.
3. **Idempotent writes:** every statement is `INSERT … ON CONFLICT DO NOTHING` (by `record_id` or a natural
   key) or an upsert by natural key. Writing a batch twice changes nothing.
4. **Outage:** when a write fails:
   - the batch and everything queued behind it are appended to **`data/wal/db.wal`** (JSONL, 0600, fsync
     per append);
   - an `AlertEvent("db_down")` is published;
   - the writer retries every 5 s.

   While the WAL holds anything, new records go to it as well, so the database always receives records in
   submission order.
5. **Recovery:** the WAL is replayed oldest first in batches, cleared, and `AlertEvent("db_recovered")` is
   published. A replay interrupted by a crash or a new outage starts over; that is safe, because the
   writes are idempotent. A WAL left by a previous process is replayed at start. A torn last line from a
   crash mid-write is skipped.
6. **WAL unwritable** (disk full): the records stay in memory, in order, and a critical `wal_write_failed`
   alert fires.
7. **Shutdown:** queued records go to the database if it's up, otherwise to the WAL.

**Bug found by the real-database test.** The writer used to copy the queue, await the WAL write, then
clear the queue. Records submitted during that await were silently dropped. It now drains the queue
synchronously before awaiting, and a regression test with a slow WAL guards it.

## Wiring (`Persistence`, `App`)

`Persistence.attach(bus, account)` subscribes to:
- each account's OMS events: orders, fills, positions, account, risk, reconcile, retry and risk-state
  events;
- portfolio alerts;
- strategy events;
- the writer's own alerts.

`put()` records reference data (accounts and instruments at start, strategies with their status at start
and stop), closed journal trades (`TradeJournal.on_closed`), and strategy state after every save
(`StrategyRunner.on_state_saved`).

`trader kill` writes an `audit_log` entry: who, what, when, result. Without a database the audit is a
no-op; with the database down it goes to the WAL.

The app starts and trades with the database down. Persistence starts first and stops last, so the final
OMS events of a shutdown are captured.

## Acceptance: DB kill test

`tests/integration/test_db_kill.py` runs the real `App` (three strategies on the paper broker) against a
dedicated PostgreSQL started by `tests/pg.py`:
1. Fills reach the database.
2. **`pg_ctl stop -m immediate`**, a hard stop with connections dropped.
3. Trading continues: more fills and orders, no strategy errors, records growing in the WAL, the writer
   reporting down.
4. PostgreSQL restarts and the WAL is replayed.
5. After shutdown the database equals the books:
   - fill ids equal the ledger;
   - order ids and final statuses equal the OMS;
   - trades equal the journal;
   - each `FillEvent` is stored exactly once;
   - the event store holds `db_down` then `db_recovered`.

`tests/integration/test_persistence_pg.py` checks every projection on a real database, the idempotent
replay, and the writer alone through a kill/restart: 150 records, all present once and in order. The
PostgreSQL tests skip when no PostgreSQL binaries are installed. CI's Ubuntu runner has them.

## Consequences

- **On a hard process crash with the database up**, the records still queued in memory (at most about one
  flush interval) are missing from the database. The local books, which are authoritative, have them. A
  backfill from the books is possible later.
- **During a long outage the WAL grows on disk** at the record rate; each record is about 1 KB.
- **Projections are rebuilt from the same records,** so a new projection can be backfilled from
  `events.payload`.
- **`docker-compose.yml` starts a local PostgreSQL 16.** The app container comes with phase 11.
